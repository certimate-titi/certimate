## 1. 現況盤點

### 1.1 含 `tenant_id` 欄位的 ORM Model（14 張）

`resource`, `resource_chunk`, `resource_scaffold`, `resource_parse_job`, `question_candidate`, `question`, `answer`, `exam`, `historical_exam`, `knowledge_node`, `syllabus_topic`, `ai_chat`, `import_task`, `import_audit_log`。

DBML 另記載 `subjects`、`user_subjects`、`users` 亦帶 `tenant_id`（migration 061 backfill 5 張表）。

### 1.2 啟用 PostgreSQL RLS 的表（僅 5 張）

| 表 | RLS 啟用點 | Policy 樣式 |
|---|---|---|
| `resource_chunks` | 038 → 061 → 064 | NULLIF（最終） |
| `answers` | 038 → 061 → 064 | NULLIF（最終） |
| `resource_parse_jobs` | 068 | NULLIF |
| `question_candidates` | 068 | NULLIF |
| `resource_scaffolds` | 068 | NULLIF |

**未啟用 RLS 但帶 tenant_id 的敏感表**：`questions`, `exams`, `knowledge_nodes`, `historical_exams`, `syllabus_topics`, `ai_chat_sessions`, `ai_chat_messages`, `import_tasks`, `import_audit_logs`, `resources`, `resource_scaffolds` 中除上表外均**只有應用層過濾**。任何漏寫 `WHERE tenant_id =` 的 query 都會跨租戶外洩。

### 1.3 GUC 命名

統一為 **`app.current_tenant_id`**（`app.tenant_id` 在程式碼中只出現於文件示例與 `backend/CLAUDE.md` 的 RLS Policy 規範段落，實際 SQL 無此用法）。命名一致，但 `CLAUDE.md` 範例與實作不符，會誤導維護者，建議統一文件。

### 1.4 設定 GUC 的 DI / 路徑

- 統一入口：`app/core/deps.py`
  - `get_db_with_tenant()` — 在 yield 前 `set_rls_tenant`，finally `RESET app.current_tenant_id`。
  - `get_current_user_with_tenant()` — 解 JWT 取 `tenant_id`，**未驗證** tenant 是否存在 / 是否該 user 所屬。
  - `set_rls_tenant()` — `db.execute(text(f"SET app.current_tenant_id = '{tid}'"))`，**用 f-string 拼接**（雖前置正則 `^[0-9a-f-]{36}$` 約束，但仍是 raw SQL 拼接反模式）。
- Worker 入口：`app/api/tasks.py`（Cloud Tasks handler）已主動 `set_rls_tenant(db, payload.tenant_id or PUBLIC_B2C_TENANT_ID)`，並於 `db.rollback()` 後**重新呼叫**一次（aborted tx 後 GUC 仍在 session 範圍，但實作為防禦）。

### 1.5 Router 端覆蓋

`grep "Depends(get_db)"` 命中 **295 處**；其中只有 `exam.py`, `wrong_answer.py`, `wrong_answer_map.py`, `knowledge_map.py`, `exam_import_async.py` 大量改用 `get_db_with_tenant`。**未改的 router 觸碰 `answers / resource_chunks / questions / resources` 等表**包括：`practice.py`, `dashboard.py`, `schedule.py`, `ai_questions.py`, `reverse_engineering.py`, `retirement.py`, `admin.py`, `resource.py`（部分）、`resource_parse.py`, `exam_import.py`, `exam_import_monitoring.py`。這些 endpoint 走 `get_db()` 時 GUC 未設，RLS 上的表會落到 `NULLIF(...) IS NULL → 視為公共 / 無限制`，**等同關閉 RLS**。

## 2. F31 BDD 15 個失敗 scenario 分類

實際 behave 結果：**15 errors, 11 undefined steps**（不是邏輯失敗，是基礎設施掛掉）。

### 類別 A — Background User 建構錯誤（污染所有 13 個 scenario）

`tests/features/steps/tenant_security/aggregate_given/tenant_student.py:19` 用了 `is_verified=True`，但 `User` model 沒這欄位（只有 `email_verified`）。Background 失敗 → 13 個 scenario 全部 errored 在第二個 Given。

### 類別 B — Step 未實作（2 個 PRD-033 scenario，11 undefined）

- `Migration 061 回填 5 張表的 NULL tenant_id`：5 個 step 全 undefined。
- `未設定 GUC 時 RLS 不應拋出 UUID cast 錯誤`：4 個 step 全 undefined。
- `散客上傳一份 PDF 資源「金融法規.pdf」`、`租戶 "company_a" 的學生使用有效帳密登入`：When/Given undefined。

### 類別 C — Cross-tenant Read（2 scenario）

L40 `租戶 A 無法查詢租戶 B 的 resource_chunks`、L47 `租戶 A 無法讀取 answers` — 邏輯本身對應 RLS 已存在的 policy，理論上會通過，但被類別 A 檔住跑不到。

### 類別 D — JWT / Auth（2 scenario）

L57 `登入後取得含 tenant_id 的 JWT`、L63 `舊 Token 向後相容` — 對應 `get_tenant_id` 中 `if not tenant_id: return PUBLIC_B2C_TENANT_ID`，**未驗證** tenant 是否與 user 對齊（IDOR 風險，見威脅模型）。

### 類別 E — SSRF（3 scenario, L74/L80/L86）

`app/core/security.py` 內含 SSRF 防護，但 step 未實作。

### 類別 F — 退場抹除（2 scenario, L96/L103）

`app/scripts/purge_tenant_data.py` 是否存在未驗證；step 未實作。

### 類別 G — BDD 隔離（2 scenario, L114/L120）

依賴 `context.test_tenant_id`，當前 environment.py 未必有設定。

**結論**：15 個失敗中 **13 個被同一個 `User(is_verified=...)` bug 連坐**；2 個 PRD-033 scenario 是真的未實作。先修 step 檔即可挽回 13 個。

## 3. 威脅模型（OWASP Top 10 對應）

| OWASP | 風險點 | 影響 |
|-------|------|------|
| A01 Broken Access Control | 295 處 `Depends(get_db)` 未走 `_with_tenant`；JWT `tenant_id` 偽造後後端不驗證歸屬 | Critical：B2B 機構 A 學生 token 改 tenant_id 欄即可讀 B 機構資料 |
| A01 IDOR | `get_tenant_id` 直接信 JWT claim，未對照 DB `users.tenant_id` | High |
| A03 Injection | `set_rls_tenant` 用 f-string 拼接 GUC（雖正則防護）+ `purge_tenant_data` 若 tenant_id 走 string format | Medium |
| A04 Insecure Design | 14 個業務表帶 `tenant_id`，僅 5 張啟用 RLS；防線只有應用層過濾 | Critical |
| A05 Security Misconfiguration | RLS policy 「GUC 為空 = 視為通行」是 fail-open 設計；任何忘設 GUC 的 endpoint 即破隔離 | Critical |
| A09 Logging | `audit_logs` 是否記錄 cross-tenant 嘗試未檢查 | Medium |

**B2B 機構導入後最可能滲透的 vector**：
1. 學生 JWT 被解碼/重簽（若 `JWT_SECRET_KEY` 外洩） → 改 `tenant_id` claim → 透過 `practice.py / dashboard.py` 等未設 GUC 路徑直讀其他機構 `questions / answers / exams`。
2. 共用 SSO 帳號被切換到別租戶後，舊 session token 仍可用（無 token rotation / revoke）。
3. 雲端 Cloud Tasks worker payload 偽造 `tenant_id`：`tasks.py` 用 `payload.tenant_id or PUBLIC_B2C` 信任輸入（OIDC 驗證簽章但 payload 內容由發起者決定）。

## 4. 建議修補順序

### Critical（生產資料外洩風險，本週內）

1. **擴大 RLS 覆蓋至所有業務表**：至少加 `questions`、`exams`、`knowledge_nodes`、`resources`、`ai_chat_sessions`，採用 NULLIF 樣式（migration 071）。
2. **改變 fail-open 策略**：RLS policy 中 `NULLIF(...) IS NULL → 通行` 改為**只允許 PUBLIC_B2C UUID 通行**：`COALESCE(NULLIF(current_setting(...),''), '00000000-0000-0000-0000-000000b2cb2c'::text)::uuid = tenant_id`。任何忘設 GUC 的 endpoint 將自動退到 public_b2c，跨租戶 0 命中。
3. **JWT tenant_id 雙重驗證**：`get_current_user_with_tenant` 應 `SELECT tenant_id FROM users WHERE id = sub` 與 JWT claim 比對；不一致回 401。

### High（兩週內）

4. **掃 295 處 `Depends(get_db)`**：凡 query 觸碰帶 `tenant_id` 的表，全改 `get_db_with_tenant`；建議加 lint rule（pre-commit）。
5. **Migration 061 / 064 殘留空字串短路**：061 policy 仍含 `OR current_setting(...) = ''`，雖被 064 取代，但 064 的 downgrade 會還原成 061 → 未來回滾即破洞；建議 migration 071 同步補強 downgrade 路徑。
6. **`set_rls_tenant` 改 bind parameter**：`db.execute(text("SET app.current_tenant_id = :tid"), {"tid": tid})` 雖 PostgreSQL `SET` 不支援 bind，可改 `SELECT set_config('app.current_tenant_id', :tid, false)`，徹底擺脫 f-string。
7. **Worker 端**：`tasks.py` 應比對 `payload.user_id` 在 DB 的 `tenant_id` 與 `payload.tenant_id` 一致，再 `set_rls_tenant`。

### Medium（一個月內）

8. 補齊 BDD step：`tenant_student.py` 改 `email_verified`；補 PRD-033 兩個 scenario step。
9. 文件 `backend/CLAUDE.md` RLS 範例的 `app.tenant_id` 改成 `app.current_tenant_id`，避免後續工程師抄錯。
10. `purge_tenant_data.py` 加入 audit log + dry-run 強制預設。

### Low

11. 整合 `get_db_with_tenant` 與 `get_current_user_with_tenant`，避免兩條 DI 並存造成混淆。
12. 移除 `tasks.py` 中 RC17/RC18 重複的 `set_rls_tenant`（現註解已說明 session GUC 不會掉，可只設一次）。

## 5. 與 Pipeline-split EPIC（RC13/RC18）的關聯

- RC13 將 `tasks.py` 加入 `set_rls_tenant(db, payload.tenant_id or PUBLIC_B2C_TENANT_ID)`，**未引入新 regression**；但 `payload.tenant_id` 由呼叫端決定，未與 user 對齊，**繼承既有 IDOR 風險**。
- RC18 在 `db.rollback()` 後重新 `set_rls_tenant`：技術上 PostgreSQL session-scoped GUC 不會被 rollback 清除，這次重設屬防禦冗餘，無害但可清理。
- Pipeline 內 `DocumentProcessingService` / `resource_parse_service` 多次 commit；`set_rls_tenant` 用 session-scoped (`SET` 而非 `SET LOCAL`) 是正確選擇，避免 commit 後 GUC 失效。
- Worker 流程的 RLS 路徑「完整」但「信任」：簽章驗證 OIDC token，**不驗證 payload 一致性**。建議於 `_verify_oidc_token` 後加 cross-check：`db.query(User).filter_by(id=payload.user_id).one().tenant_id == payload.tenant_id`。

## 回報摘要

- Critical：3（RLS 覆蓋率不足、fail-open policy、JWT tenant_id 未雙重驗證）
- High：4（295 處 `get_db` 漏設 GUC、061 downgrade 殘留空字串短路、`set_rls_tenant` f-string 拼接、worker payload 信任）
- Medium：3（BDD step 不一致 + 未實作、文件 GUC 名稱錯、purge 腳本驗收 step 缺）
- Low：2（DI 命名重複、tasks.py 重複設 GUC）

**建議立刻修**：
1. 修 `tenant_student.py` 的 `is_verified → email_verified`，挽回 13 個 BDD scenario 不再 error。
2. 起 migration 071 把 RLS policy 從「fail-open（GUC 空 = 通行）」改成「fall-through to PUBLIC_B2C」；同時為 `questions / exams / resources / knowledge_nodes / ai_chat_sessions` 補 RLS。
3. `get_current_user_with_tenant` 加 DB 對齊驗證，斷掉 IDOR 路徑。

其餘排入兩週內 sprint；BDD 三題（PRD-033 scenario + SSRF/purge step）待 step 補齊後再跑一次 F31 驗收。
