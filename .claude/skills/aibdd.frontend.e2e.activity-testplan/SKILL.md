# Activity Test Plan 產生器

從 Activity Diagram + 網頁 UI 推導瀏覽器驗收測試計畫。

## 兩大輸入來源與職責

| 來源 | 提供什麼 | 權重 |
|------|---------|------|
| **網頁 UI** | 每個動作在 UI 上的具體測試行為：點哪裡、填什麼、看到什麼 | **主要**（測試細節的唯一真相來源） |
| **Activity Diagram** | 動作之間的流程組織：路線、分支、迴圈、並行、情境劃分 | **輔助**（結構骨架） |

### 網頁 UI 的兩種形式

1. **靜態雛形**（HTML/設計稿）：尚未實作的參考原型。AI 應分析頁面結構、元件配置、文字標籤，推導出操作步驟和預期結果。
2. **已實作的前端應用**（Next.js App 等）：可直接瀏覽的運行中應用。AI 應實際瀏覽頁面，觀察真實的 UI 元素、互動行為、頁面導航，據此撰寫精確的測試步驟。

### 為什麼網頁 UI 是主要參照

Activity Diagram 描述的是抽象流程（「設定自動化」→「激活名單」），本身不包含 UI/UX 的測試細節。真正的測試行為——點擊哪個按鈕、在哪個欄位輸入什麼值、畫面上會出現什麼回饋——只有從網頁 UI 上才能觀察到。

Activity Diagram 的價值在於：告訴你有幾條路線、每條路線走過哪些分支、情境如何組織。但「路線上每一步具體怎麼測」，必須看網頁。

```
1. 分析網頁 UI    — 瀏覽或閱讀網頁，理解每個動作的 UI 測試行為
2. 解析 Activity   — 讀取 .activity 檔，識別節點、分支、合流
3. 路徑枚舉        — 以路徑覆蓋策略展開所有測試路線
4. 情境命名        — 為每條路線產生描述性名稱
5. 步驟精煉        — 結合 UI 觀察與流程結構，產出操作描述 + 預期結果
6. 產出 Test Plan  — 輸出 Markdown 格式測試計畫
```

## Phase 1：分析網頁 UI

這是測試計畫品質的關鍵步驟。根據使用者提供的網頁類型進行分析：

**若為靜態雛形：**
- 閱讀 HTML 原始碼或設計稿
- 識別頁面結構：導航列、表單、按鈕、表格、對話框等互動元件
- 記錄每個可操作元件的位置、標籤文字、預期行為

**若為已實作的前端應用：**
- 實際瀏覽應用，走過主要 User Flow
- 觀察並記錄：頁面 URL 結構、導航路徑、表單欄位、按鈕位置、回饋訊息
- 注意互動細節：Loading 狀態、Toast 通知、Modal 確認框、表單驗證訊息

**產出：** 建立一份心智模型，記錄每個動作對應的 UI 操作方式和可觀察的結果。此心智模型將在 Phase 5 步驟精煉時使用。

## Phase 2：解析 Activity

讀取 `.activity` 檔，識別以下結構元素：

| 元素 | 語法 | 測試意義 |
|------|------|----------|
| 步驟 | `[STEP:N]` | 一個可操作的測試步驟 |
| 決策 | `[DECISION:Nx]` | 分支點，產生多條路線 |
| 分支 | `[BRANCH:Nx:條件]` | 分支的特定條件路徑 |
| 回流分支 | `[BRANCH:Nx:條件 -> M]` | 迴圈行為，跳回特定步驟 |
| 合流 | `[MERGE:Nx]` | 分支重新匯合 |
| 並行開始 | `[FORK:Nx]` | 並行路徑開始 |
| 並行路徑 | `[PARALLEL:Nx]` | 並行執行的獨立路徑 |
| 並行結束 | `[JOIN:Nx]` | 並行路徑匯合 |
| 結束 | `[END]` | 流程終點 |

每個 `STEP` 和 `BRANCH` 可能綁定 `.feature` 或 `.md` 檔案作為補充規格。但這些檔案**不是測試行為的主要來源**——網頁 UI 才是。

## Phase 3：路徑枚舉

採用**路徑覆蓋**策略推導測試路線。詳細演算法見 [references/path-coverage.md](references/path-coverage.md)。

核心規則：

1. **線性步驟**：直接串接為路線的連續步驟。
2. **DECISION 分支**：每個分支條件產生一條獨立路線。N 個分支 = N 條路線。
3. **多層 DECISION**：取笛卡爾積。例如 DECISION A（2 分支）後接 DECISION B（2 分支）= 4 條路線。
4. **回流分支（Loop）**：產生一條「迴圈路線」，在該路線中走到回流分支後，跳回目標步驟重新執行一輪，然後走另一條出口分支離開。
5. **FORK 並行**：所有 PARALLEL 路徑合併為單一測試路線中的多個驗證步驟（先驗證路徑 A 的結果，再驗證路徑 B 的結果）。

## Phase 4：情境命名

每條路線的名稱必須**直接反映該路線的特色**，格式：

```
[Activity名稱] — [路線特色描述]
```

命名規則：
- 以分支條件組合作為特色描述
- 線性流程（無分支）命名為「正常流程」或「完整流程」
- 包含迴圈的路線加上「（含重試）」或「（含迴圈）」
- 名稱必須讓人一眼看出這條路線走了哪些分支

## Phase 5：步驟精煉

這是整合兩大來源的核心步驟。

**流程結構**來自 Activity Diagram：哪些步驟、什麼順序、走哪個分支。
**測試細節**來自網頁 UI：具體點哪裡、填什麼、看到什麼。

### 精煉優先順序

1. **首先參考網頁 UI**：根據 Phase 1 的分析結果，撰寫具體的瀏覽器操作和可觀察的 UI 回饋。
2. **再對照 Activity 節點**：確認該步驟在流程中的位置和上下文，確保操作描述符合當前情境（例如：同一個頁面在不同分支條件下，可能顯示不同狀態）。
3. **最後參考綁定的 .feature / .md 檔案**（若存在）：作為補充資訊，驗證步驟的完整性。

### 預期結果精煉要求

預期結果是 AI 自動化驗收的關鍵，必須：

1. **可觀察**：描述 UI 上可見的變化（文字、元素、狀態）
2. **可驗證**：給出具體的檢查項，而非模糊描述
3. **多項條列**：一個步驟可有多個檢查項，用條列式列出
4. **來自真實 UI**：操作描述和預期結果必須基於網頁 UI 的實際觀察，不可憑空臆造

## Phase 6：產出 Test Plan

輸出格式見 [references/testplan-format.md](references/testplan-format.md)。

完整範例見 [references/example-testplan.md](references/example-testplan.md)，
該範例使用「名單激活」Activity 作為輸入，展示 4 條路線的完整測試計畫。

### 產出檔案位置

測試計畫寫入與 `.activity` 檔同層目錄，檔名為 `<activity名稱>.testplan.md`。

## 注意事項

- **先分析網頁 UI 再精煉步驟**。網頁 UI 是測試行為的主要依據。
- **Activity Diagram 決定「測什麼路線」，網頁 UI 決定「怎麼測」**。兩者職責不同，不可混淆。
- **不要臆造 UI 操作**。所有操作描述都必須有 UI 依據（來自實際網頁觀察或雛形分析）。若網頁中找不到對應的 UI 元素，該步驟標註 `[待補：UI 尚未實作]`。
- **綁定的 .feature / .md 檔案是補充參考**，不是測試行為的主要來源。若檔案不存在，不影響測試計畫的產出（只要網頁 UI 有對應的內容）。
- **繁體中文產出**。所有內容使用繁體中文。
