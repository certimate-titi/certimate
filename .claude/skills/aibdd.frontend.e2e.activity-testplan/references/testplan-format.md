# 測試計畫格式規範

## 文件結構

```markdown
# [Activity 名稱] — 驗收測試計畫

> 來源：[.activity 檔案路徑]
> 產生日期：[YYYY-MM-DD]
> 測試路線數：[N]

---

## 路線總覽

| # | 情境名稱 | 分支條件 | 步驟數 |
|---|---------|---------|--------|
| 1 | [情境名稱] | [走過的分支條件] | [N] |
| 2 | [情境名稱] | [走過的分支條件] | [N] |

---

## 情境 1：[情境名稱]

**路線描述**：[一句話描述這條路線走過的路徑]

|---|---------|---------|
| 1 | [具體的瀏覽器操作] | [可驗證的 UI 狀態] |
| 2 | [具體的瀏覽器操作] | [可驗證的 UI 狀態] |

---

## 情境 2：[情境名稱]

...（同上格式）
```

## 欄位撰寫規範

### 操作描述

描述在瀏覽器上執行的具體操作，必須精確到可重現：

**好的寫法：**
- 「點擊左側導航列的『名單管理』連結」
- 「在『姓名』欄位輸入 `王小明`，在『信箱』欄位輸入 `wang@example.com`」
- 「點擊表格第一列的『編輯』按鈕」
- 「在搜尋框輸入 `測試` 後按 Enter」

**不好的寫法：**
- 「進入名單頁面」（太模糊，沒說怎麼進入）
- 「填寫表單」（沒說填哪些欄位、填什麼值）
- 「操作編輯功能」（不具體）

### 預期結果

描述操作後 UI 上可觀察、可驗證的狀態。每個檢查項用條列式列出：

**好的寫法：**
```
- 頁面顯示成功訊息「名單已成功建立」
- 表格新增一列，顯示姓名「王小明」
- URL 變更為 `/leads/123`
- 「儲存」按鈕變為不可點擊狀態
```

**不好的寫法：**
```
- 操作成功（太模糊）
- 資料已儲存（無法從 UI 驗證）
- 系統正常運作（無法觀察）
```

### 預期結果的檢查項類型

| 類型 | 說明 | 範例 |
|------|------|------|
| 文字內容 | 頁面上出現/消失特定文字 | 「顯示訊息：『匯入成功，共 5 筆』」 |
| 元素狀態 | UI 元素的可見性、可用性 | 「『送出』按鈕變為可點擊狀態」 |
| 導航變化 | URL 或頁面切換 | 「頁面導向 `/leads` 清單頁」 |
| 資料呈現 | 表格、清單、卡片的內容 | 「表格顯示 3 筆資料，包含欄位：姓名、信箱、狀態」 |
| 表單狀態 | 輸入欄位的預設值、驗證訊息 | 「姓名欄位下方顯示紅色提示『此欄位為必填』」 |
| 視覺回饋 | Toast、Modal、Loading 等 | 「右上角出現綠色 Toast 通知」 |
