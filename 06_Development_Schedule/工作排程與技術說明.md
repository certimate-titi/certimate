# 工作排程與技術說明

## 📅 一、詳細工作排程與開發里程碑 (2026 Q2 ~ Q4)

我們將時程分為三大階段，從 MVP 驗證到正式商轉擴張：

### Phase 1: 概念驗證與 MVP 開發 (2026 Q2)
- **M1 (4月)：基礎架構建立與 AI 驗證**
  - **基礎設施**：建立 Google Cloud 開發環境，包含 Cloud Run、Cloud SQL (PostgreSQL)、Google Cloud Storage (GCS)。
  - **資料庫**：設計關聯式 Schema (使用者、訂閱狀態、測驗歷史) 與啟用 `pgvector` 處理向量資料。
  - **AI 整合**：串接 OpenRouter，進行 Prompt Engineering 測試 (著重在知識提取與 JSON 格式化輸出的穩定度)。
- **M2 (5月)：後端 Pipeline 與資料解析核心**
  - **Main API (Node.js/Go)**：建置基礎 CRUD，處理會員登入狀態與資料庫互動。
  - **AI Worker (Python)**：完成非同步處理機制。實作文檔解析 (Unstructured.io)、Vision OCR (數學與手寫辨識轉 KaTeX)，以及多語言 Embedding 切塊存入 Vector DB。
  - **MCP 服務**：開發 `youtube-transcript-mcp-server` 獨立服務。
- **M3 (6月)：前端實作與內部 MVP 測試**
  - **前端 (Next.js/Vue)**：完成核心介面：包含資料上傳介面、線上測驗渲染 (支援 KaTeX 數學公式)，以及錯題檢閱區塊。
  - **系統串接**：完成「上傳 -> Pub/Sub 排隊 -> Python Worker 處理 -> WebSocket/SSE 通知前端」的異步資料流。

### Phase 2: 封閉測試與系統迭代 (2026 Q3)
- **M4 (7月)：Closed Beta (100 位白老鼠測試)**
  - 啟動 User Tracking，收集錯誤日誌與真實使用行為。
  - 測試大流量上傳時系統資源的排隊與容錯率。
- **M5 (8月)：成效調優與成本控制**
  - **AI 幻覺控制**：優化 RAG 檢索邏輯，導入「非題庫問題」的防護網與冷卻機制。
  - **快取實作**：導入 Google Cloud Memorystore (Redis)，針對熱門素材實作 `doc_hash` 命中機制，大幅節省 Token 費用。
- **M6 (9月)：準備 Public Beta (金流與權限)**
  - 導入 Firebase Authentication (Email + Google OAuth 一鍵登入)。
  - 串接 Stripe/綠界，處理 199 TWD Pro 版的訂閱與權限開通，實作 Free / Pro 雙軌 API 限制。

### Phase 3: 正式上線與商業擴張 (2026 Q4)
- **M7 (10月)：v1.0 正式上線**
  - 在 Cloud Run 前端加上 API Gateway 或 Firebase App Check 防範 DDoS 惡意攻擊。
  - 配合行銷團隊展開第一波宣傳與 SEO (利用 Next.js SSR 優勢)。
- **M8 (11月)：商業模式優化**
  - 導入廣告聯播網，並透過數據優化免費用戶轉換至 Pro 方案的漏斗 (如：錯題教練的引導 UI)。
- **M9 (12月)：B2B SaaS 準備**
  - 評估企業端/補習班講師的需求，為機構版分支做底層系統的租戶隔離 (Multi-Tenancy) 規劃。

## 💻 二、關鍵技術使用說明與架構守則

為了讓系統保持高可用性 (HA) 與方便維護，團隊在開發時必須嚴格遵守以下架構設計模式：

### 1. 徹底的非同步事件驅動設計 (Event-Driven Architecture)
- **問題情境**：處理 10 小時 Youtube 或是 100 頁微積分筆記非常耗時，若用傳統 HTTP 同步等待必將 Timeout。
- **使用說明**：
  - 前端上傳檔案至 GCS，後端 Main API 馬上回傳一個 `TaskID` 給前端。
  - GCS 上傳觸發 **Google Cloud Pub/Sub**，把任務送進 **Python AI Worker**。
  - Worker 完成切塊 (Chunking)、Vector Embedding 與考題生成後，透過 WebSocket 或 SSE (Server-Sent Events) 即時推播更新給前端通知「考卷已備妥」。

### 2. OpenRouter 動態模型路由與備援
- **問題情境**：綁死單一 LLM 供應商風險極高 (當機或無故漲價)，且殺雞焉用牛刀。
- **使用說明**：
  - 系統內部不直接呼叫 OpenAI/Anthropic API，一律通過 **OpenRouter** 單一入口。
  - **Free 用戶及簡單任務**：程式邏輯自動切換到成本極低的 `gemini-1.5-flash` 或 `llama-3-8b`。
  - **Pro 用戶及複雜任務 (數學 OCR / 蘇格拉底教練)**：自動提升至 `claude-3.5-sonnet` 或 `gpt-4o` 確保邏輯與 LaTeX 語法正確。
  - **高可用性**：配合備援邏輯，如果 A 模型 Timeout，程式可在 1 毫秒內 fallback 到同級別的 B 模型，不中斷用戶體驗。

### 3. 模組化解析微服務：MCP (Model Context Protocol)
- **問題情境**：未來可能增加 Notion、Podcast 等多元資料源，全部寫在一個後端會變成難以維護的巨石架構 (Monolith)。
- **使用說明**：
  - 將各類資料的爬蟲或解析器獨立為微服務。例如：Youtube 字幕解析，直接打包成 `youtube-transcript-mcp-server`。
  - 主程式藉由 MCP 協定請求解析後的純文字即可。未來若要新增載體，只要擴充對應的 MCP Server，主專案完全無需改動程式碼。

### 4. 安全與成本防護牆 (Guardrails & Rate Limiting)
- **問題情境**：免費用戶無限制消耗問答 Token，或詢問不相關的問題產生無謂成本。
- **使用說明**：
  - **快取命中 (Cache Hit)**：對於同一文件的請求，在解析前先比對 Redis 內的 `doc_hash`，若命中則直接繞過 LLM 提取既有資料，達到 100% 邊際成本下降。
  - **回答範圍限制**：發送給 LLM 之前，先經過 RAG Vector 檢索。如果相關性過低，代表該問題超綱，直接回傳固定字串：「*此問題超出目前題庫範圍，請上傳相關學習資源後再試。*」，**不觸發 LLM 計費**。
  - **短路冷卻機制**：搭配 Redis，10 分鐘內觸發 5 次惡意問答的使用者，強制暫停該用戶問答功能 30 分鐘，有效阻斷免費白嫖腳本。
