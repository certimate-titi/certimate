# 工作排程與技術說明

## 📅 一、詳細工作排程與開發里程碑 (2026 Q2 ~ Q4)

我們將時程分為三大階段，從 MVP 驗證到正式商轉擴張：

### Phase 1: 概念驗證與 MVP 開發 (2026 Q2)
- **M1 (4月)：基礎架構建立與 AI 驗證**
  - **基礎設施**：建立 Google Cloud 開發環境，包含 Cloud Run、Cloud SQL (PostgreSQL + pgvector)、Google Cloud Storage (GCS)。
  - **資料庫**：設計 Schema（Users、Subscriptions、Resources、Flashcards、LearningSchedule）並啟用 `pgvector` 與 `pg tsvector` 混合搜尋。
  - **AI 整合**：串接 OpenRouter，驗證 `gemini-1.5-flash`（低成本基底）與 `claude-3.5-sonnet`（Pro Plus 高階任務）的 Prompt 穩定性。
- **M2 (5月)：後端 Pipeline 與資料解析核心**
  - **Main API (Node.js/Go)**：建置基礎 CRUD，處理會員登入狀態與資料庫互動。
  - **AI Worker (Python)**：完成非同步處理機制。實作文檔解析、Vision OCR（數學與手寫辨識，**僅限 Pro Plus 觸發**），以及多語言 Embedding 切塊存入 pgvector。
  - **雙軌儲存 (Dual-Storage)**：解析成功 (COMPLETED) 後寫入 GCS .md + pgvector，並靜默刪除原始檔；解析失敗 (FAILED) 則保留原始檔，等待使用者重試。
  - **MCP 服務**：開發 `youtube-transcript-mcp-server` 獨立服務。
- **M3 (6月)：前端實作與內部 MVP 測試**
  - **前端 (Next.js)**：完成核心介面：資料上傳區（含 Pro Plus Vision OCR 方案門檻 Paywall）、線上測驗渲染（KaTeX 數學公式）、解析進度三段式回饋（PENDING / COMPLETED / FAILED 重試按鈕）。
  - **系統串接**：完成「上傳 → Pub/Sub 排隊 → Python Worker 處理 → SSE 通知前端」的異步資料流。

### Phase 2: 封閉測試與系統迭代 (2026 Q3)
- **M4 (7月)：Closed Beta (100 位封測)**
  - 啟動 User Tracking，收集錯誤日誌與真實使用行為。
  - 測試大流量上傳時系統資源的排隊與容錯率。
- **M5 (8月)：成效調優與成本控制**
  - **AI 幻覺控制**：優化 RAG 檢索邏輯，導入「非題庫問題」的防護網與冷卻機制。
  - **快取實作**：導入 Google Cloud Memorystore (Redis)，針對熱門素材實作 `doc_hash` 命中機制，大幅節省 Token 費用。
  - **三階層限速**：實作 Free / Pro / Pro Plus / Ultra 各自的 API Rate Limit 與 Claude 教練配額管控（Pro Plus 200 次/月）。
- **M6 (9月)：準備 Public Beta（金流與三階層權限）**
  - 導入 Firebase Authentication (Email + Google OAuth 一鍵登入)。
  - 串接 Stripe/綠界，配置 **199 TWD (Pro) / 399 TWD (Pro Plus) / 1599 TWD (Ultra)** 三種定期定額訂閱商品。
  - 實作 Free / Pro / Pro Plus / Ultra 四軌 API 權限分隔 (RBAC Middleware)。

### Phase 3: 正式上線與商業擴張 (2026 Q4)
- **M7 (10月)：v1.0 正式上線**
  - 在 Cloud Run 前端加上 API Gateway 或 Firebase App Check 防範 DDoS 惡意攻擊。
  - 配合行銷團隊展開第一波宣傳與 SEO (利用 Next.js SSR 優勢)。
- **M8 (11月)：商業模式優化與資料智能**
  - 漏斗優化：追蹤知識心智圖頁「毛玻璃鎖」的點擊率到 Pro Plus 轉換率，A/B 測試升級提示文案。
  - Sprint / Standard / Mastery 三模式動態排程演算法正式上線，驗證留存率提升效果。
- **M9 (12月)：B2B SaaS 啟航 (Ultra 方案後台)**
  - 實作機構管理後台（Ultra 限定）：席位派發 (Seat Management)、CSV 批次匯入學員、班級弱點熱力圖、AI 個人化補強建議。
  - 多租戶架構 (Multi-Tenancy)：確保補習班 A 的學員資料完全隔離於補習班 B。
  - 平台超級管理後台：AI 成本即時燃燒圖、毛玻璃 Paywall 轉換漏斗、異常用戶偵測（濫用/共帳防護）。

## 💻 二、關鍵技術使用說明與架構守則

為了讓系統保持高可用性 (HA) 與方便維護，團隊在開發時必須嚴格遵守以下架構設計模式：

### 1. 徹底的非同步事件驅動設計 (Event-Driven Architecture)
- **問題情境**：處理 10 小時 YouTube 或是 100 頁微積分筆記非常耗時，若用傳統 HTTP 同步等待必將 Timeout。
- **使用說明**：
  - 前端上傳檔案至 GCS，後端 Main API 馬上回傳一個 `TaskID` 給前端。
  - GCS 上傳觸發 **Google Cloud Pub/Sub**，把任務送進 **Python AI Worker**。
  - Worker 完成切塊、Vector Embedding 與考題生成後，透過 SSE 即時推播更新（PENDING → COMPLETED 或 FAILED）給前端，原始檔的刪除動作在此階段靜默完成。

### 2. OpenRouter 動態模型路由與備援
- **問題情境**：綁死單一 LLM 供應商風險極高（當機或無故漲價），且殺雞焉用牛刀。
- **使用說明**：
  - 系統內部一律通過 **OpenRouter** 單一入口。
  - **Free 用戶及簡單任務（PDF/YouTube → 出題）**：自動切換至 `gemini-1.5-flash`（成本最低）。
  - **Pro Plus 用戶的 Vision OCR 與 Claude 教練**：自動提升至 `claude-3.5-sonnet` 或 `gpt-4o-vision`，確保手寫公式辨識與教學品質。
  - **高可用性**：A 模型 Timeout 時，1ms 內 Fallback 到同級 B 模型，不中斷使用者體驗。

### 3. 模組化解析微服務：MCP (Model Context Protocol)
- **問題情境**：未來可能增加 Notion、Podcast 等多元資料源，全部寫在一個後端會變成難以維護的巨石架構。
- **使用說明**：
  - 各類資料的解析器獨立為微服務，如 `youtube-transcript-mcp-server`。
  - 主程式藉由 MCP 協定請求純文字即可；新增載體只需擴充對應 MCP Server，主專案零改動。

### 4. 安全與成本防護牆 (Guardrails & Rate Limiting)
- **問題情境**：免費用戶無限制消耗 Token，或 Pro Plus 額度內的 Claude 被惡意腳本清空。
- **使用說明**：
  - **快取命中 (Cache Hit)**：上傳前比對 Redis `doc_hash`，同一份文件 100% 節省 LLM 費用。
  - **回答範圍限制**：RAG 相似度過低視為超綱題，回傳固定字串，**不觸發 LLM 計費**。
  - **短路冷卻機制**：10 分鐘內惡意問答 5 次，強制冷卻 30 分鐘。
  - **Claude 月配額守門員**：Pro Plus 每月 200 次教練額度，用盡後前端顯示「本月額度已用完，下個計費週期自動恢復」，不允許超額消費。
