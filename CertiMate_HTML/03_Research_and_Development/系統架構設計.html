系統架構設計

1. 架構總覽

本專案採用前後端分離 (Decoupled Architecture) 與微服務/無伺服器 (Serverless) 概念混合，以達到高擴展性與低維護成本。

2. 前端開發 (Frontend)

  • 框架：Next.js (React) 或 Vue/Nuxt.js (根據團隊偏好)，支援 SEO 與 SSR/SSG。
  • UI 函式庫：TailwindCSS + UI 元件庫 (例如 Shadcn UI)。
  • 部署：Google Cloud Run (若前端為 SSR) 或 Firebase Hosting (若為純靜態 SSG)。

3. 後端開發 (Backend & API)

  • 核心架構：採用微服務架構 (Microservices) 或模組化單體 (Modular Monolith) 部署於 Google Cloud Run。
  • 框架選擇：
    • Main API (CRUD): Node.js (Express/NestJS) 或 Go，負責處理會員狀態、金流狀態、與測驗歷史。
    • AI Worker (非同步): Python (FastAPI/Celery)，專職處理吃重資源的 PDF 預處理、PDF/圖片的 Vision OCR 轉換、與呼叫 OpenRouter 進行 Embedding/生成。

4. 基礎設施與外部服務 (Infrastructure & GCP Services)

  • 關聯式資料庫：Google Cloud SQL (PostgreSQL) 儲存用戶屬性、訂閱層級 ($199 Pro 版權限) 與測驗資料。
  • 向量資料庫：Pinecone 或 Cloud SQL 的 pgvector 擴充套件，將關聯與向量檢索合而為一，降低維護複雜度。
  • 檔案儲存：Google Cloud Storage (GCS) 存放用戶上傳之講義、PDF 與數學手寫圖片。
  • 背景任務與定時服務：Google Cloud Pub/Sub 搭配 Cloud Run 處理高耗時的解析任務 (特別是長篇 YouTube 或複雜圖表 PDF)；Google Cloud Scheduler 處理定時清整與艾賓浩斯複習推播。
  • AI 引擎 (LLM Gateway)：全面導入 OpenRouter 作為統一的 API 閘道端點 (Endpoint)。不綁死單一雲端廠商，系統依照使用者的定價層級 (Free/Pro) 與任務複雜度，動態路由至 Gemini 1.5 Flash (極速), Claude 3.5 Sonnet (高階解析), GPT-4o, 或各類開源 Llama 模型。
  • 身分驗證與金流：
    • 註冊與登入：以 Email 作為主要帳號識別，使用者可透過 Email/密碼註冊。同時支援 Gmail 帳號綁定，透過 Firebase Authentication 的 Google OAuth Provider 實現一鍵登入與帳號關聯。
    • 金流：Stripe (或綠界) 處理 199 TWD 的定期定額訂閱扣款。
  • 快取層與防禦機制 (Caching & Rate Limiting)：導入 Google Cloud Memorystore (Redis)。
    1. 攔截 API 異常呼叫 (如極端高頻匯出、羊毛黨腳本)。
    2. 快取 (doc_hash) 已解析過的熱門講義或 YouTube，一旦快取命中 (Cache Hit)，直接繞過 LLM 省下 100% 的 Token 費用，形成規模化後的暴利邊際效應。

5. 架構優化與擴充性設計 (Scalability & Extensibility)

為了應對未來用戶增長 (如免費流量暴增) 與功能迭代 (如 YouTube 解析)，系統架構上採取了以下進階設計來確保未來擴充無礙：

A. API Gateway 與 OpenRouter 雙層隔離策略

  • 隨著 Free 與 Pro 訂閱層級的區分，未來將在 Cloud Run 前端加上 Google Cloud API Gateway 或 Firebase App Check，阻絕免費用戶惡意 DDOS。
  • 而在後端對 LLM 的呼叫層，一律透過 OpenRouter。這創造了巨大的彈性：若某家廠商 (如 OpenAI) 當機或漲價，系統可以透過程式碼條件判斷，在 1 毫秒內將流量無痛切換至備援模型 (如 Anthropic 或 Google)，確保平台服務不中斷 (High Availability)。

B. MCP (Model Context Protocol) 插件式微服務

  • 面對 YouTube 長影音甚至未來的 Podcast、Notion 講義等多元的「知識載體」，我們不把所有爬蟲或解析邏輯塞進主後端 (Monolith)。
  • 我們採用 MCP 架構，把「YouTube 字幕解析器」獨立成一個微服務 (Cloud Run)。主程式只需要透過標準 MCP 協議呼叫它，取得乾淨的純文字。這極大化了系統的解耦 (Decoupling)，未來擴充新文件源只需寫一個新的 MCP Server 即可。

C. 非同步非阻塞的事件驅動 (Event-Driven)

  • 處理長達 10 小時的 YouTube 逐字稿或使用 Vision OCR 解析 100 頁微積分手寫筆記，若是同步等待 (Synchronous) 會導致連線 Timeout 且霸佔前端資源。
  • 採用徹底的 Event-Driven 架構：前端上傳後拿到一個 TaskID 即刻返回，後端由 Cloud Pub/Sub 將龐大任務扔到背景的 Python AI Worker 慢慢切塊 (Chunking)、辨識數學公式 (KaTeX 轉譯) 與 Embedding。完成後再透過 WebSocket 或 Server-Sent Events (SSE) 即時推播 (Push) 通知前端「考卷已生成」。

6. 系統資料流 (Data Flow) - 以手寫理工圖片為例

  1. Pro 用戶上傳包含手寫方程式的照片/PDF -> 進入 GCS 儲存。
  2. GCS 上傳事件觸發 Pub/Sub -> 喚醒 Python AI Worker。
  3. Worker 偵測到圖檔，拉取影像並呼叫 GPT-4o (Vision) 或 Claude 3.5 進入「複雜數學 OCR 降維打擊管線」。
  4. Vision 模型將手寫筆記轉錄為帶有多個 $$...$$ (KaTeX) 語法的 Markdown 純文字。
  5. Chunk 過的 Markdown 文字送入 Embedding Model -> 存入 Vector DB。
  6. 後續當使用者點擊「開始測驗」，前端 App 拉取題目並透過 KaTeX 函式庫將 $$...$$ 完美渲染為高尚的線上數學考卷。
