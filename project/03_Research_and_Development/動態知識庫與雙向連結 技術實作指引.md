# 🛠️ TiTi 核心架構：結果導向與動態記憶圖譜 系統設計規格書 (TDD)

**文件狀態：** 最終確認版 (Production Ready - V4)
**目標受眾：** Backend Engineers, Frontend Engineers, Data Engineers
**專案代號：** TiTi-Memory-Graph

## 一、 系統架構總覽 (Architecture Overview)

### 1.1 核心定義：具備半衰期的數位雙生
TiTi 的動態知識圖譜是一個會隨時間與測驗結果「有機生長與衰退」的系統。
* **靜態骨架 (Static Backbone)：** 由 AI 逆向工程萃取的官方考綱（支援動態新增與軟合併，無版本切換）。
* **結果導向 (Assessment-Driven)：** 日常「沙盒練習」不寫入圖譜。只有在正式測驗（無詳解、有計時）交卷後，才將成績視為有效數據注入狀態機。
* **記憶衰退 (Time-Weighted Decay)：** 節點進度不再是靜態數值，而是隨時間流逝自然衰退的有機體，精準反映考生的「當下真實實力」。

### 1.2 解決的核心業務痛點
1. **假性掌握：** 排除練習時看詳解答對的雜訊，確保圖譜 100% 反映真實考場實力。
2. **考綱改版導致資料遺失：** 透過「軟合併與動態重算」，無痛吸收考點的增刪改。
3. **過期實力的高估：** 引入記憶衰退機制，打破「一個月前考 100 分等於現在會 100 分」的迷思。

## 二、 核心資料庫設計 (Database Schema)

資料庫不儲存絕對的「當前進度」，而是儲存「基礎實力」與「時間錨點」。

### 2.1 考綱骨架表：`syllabus_topics` (有機考綱樹)
```sql
CREATE TABLE syllabus_topics (
    id UUID PRIMARY KEY,
    parent_id UUID REFERENCES syllabus_topics(id),
    name VARCHAR(255) NOT NULL,
    depth INT NOT NULL,                            
    weight FLOAT DEFAULT 1.0,                      
    prerequisite_topic_id UUID REFERENCES syllabus_topics(id), -- 溯源錨點
    
    is_active BOOLEAN DEFAULT TRUE,                -- 軟刪除標記
    merged_into_id UUID REFERENCES syllabus_topics(id), -- 整併繼承指標
    
    created_at TIMESTAMPTZ DEFAULT NOW(),
    updated_at TIMESTAMPTZ DEFAULT NOW()
);
```

### 2.2 個人狀態聚合表：`user_topic_states` (記憶錨點)
**(重大變更)** 此表不再儲存 `progress_percentage`，改為儲存演算法所需的底層參數。

```sql
CREATE TABLE user_topic_states (
    user_id UUID REFERENCES users(id),
    topic_id UUID REFERENCES syllabus_topics(id),
    
    status VARCHAR(20) DEFAULT 'UNSEEN',           -- UNSEEN, CRITICAL, PENDING, MASTERED
    base_mastery FLOAT DEFAULT 0.0,                -- 基礎實力 (來自歷次正式測驗的加權)
    ease_factor FLOAT DEFAULT 2.5,                 -- SM-2 難易度參數 (決定衰減速度)
    
    last_tested_at TIMESTAMPTZ,                    -- 最後一次正式測驗的時間
    next_review_at TIMESTAMPTZ,                    -- 預計開始衰退的起點時間
    
    PRIMARY KEY (user_id, topic_id)
);
```

## 三、 動態衰退與重算引擎 (Decay & Computation Engine)

為防止資料庫被背景衰退排程寫爆，系統採用**「讀取時動態計算 (Read-time Computation)」**。

### 3.1 記憶保留率演算法 (Client-side / API Read-time)
當讀取圖譜時，帶入當前時間戳記 $t_{now}$ 進行即時計算：

$$\text{Retention} = \begin{cases} 1.0, & \text{if } t_{now} \le \text{next\_review\_at} \\ \max(0.7, e^{-\lambda (t_{now} - \text{next\_review\_at})}), & \text{if } t_{now} > \text{next\_review\_at} \end{cases}$$

*(註：保留率設有底線 $0.7$，確保衰退最多扣除 30% 實力，避免引發學生過度恐慌。$\lambda$ 為基於 `ease_factor` 的衰減係數。)*

### 3.2 最終顯示百分比 (Effective Progress)
前端畫面上所有節點的百分比，皆由此公式得出：

$$\text{Effective Progress} = \text{base\_mastery} \times \text{Retention}$$

### 3.3 向上渲染加總 (Upward Propagation)
**(重大變更)** 由於底層葉節點每分每秒都在衰退，**父層級（章/節）的進度必須交由 Client-side (前端 Web Worker) 即時遞迴加總**。
* 邏輯：父節點 Effective Progress = $\sum (\text{子節點 Effective Progress} \times \text{子節點權重}) / \text{總權重}$。
* 效益：徹底解放伺服器運算壓力，達成 Zero DB I/O。

## 四、 後端業務邏輯與 API 設計 (Backend API)

必須嚴格隔離「沙盒練習」與「正式測驗」。

### 4.1 隔離的 API 路由
* `POST /api/practice/submit`：回傳對錯與詳解，**不更新** `user_topic_states`。
* `POST /api/exams/{exam_id}/submit`：接收整份考卷 Payload，寫入 Message Queue，觸發非同步狀態結算。

### 4.2 非同步批次結算 (Exam Session Settlement)
背景 Celery Worker 處理交卷 Payload 時，必須遵守以下時序原則：

```python
@celery.task
def process_exam_submission(user_id: str, exam_payload: list[dict]):
    # 1. 嚴格時序重播 (Chronological Replay)
    # 依照學生作答的時間戳記排序，避免「同考點多題」的狀態壓縮衝突
    sorted_answers = sorted(exam_payload, key=lambda x: x['answered_at'])
    
    topic_updates = {}
    for answer in sorted_answers:
        topic_id = answer['topic_id']
        # 依序更新記憶體中的 base_mastery, ease_factor, next_review_at
        topic_updates[topic_id] = apply_sm2_state_machine(topic_updates.get(topic_id), answer)
        
    # 2. 批次寫入 (Bulk Update)
    db.session.bulk_update_mappings(UserTopicState, topic_updates.values())
    db.session.commit()
    
    # 3. 通知前端結算完成
    websocket.send(user_id, {"event": "EXAM_SETTLED"})
```

## 五、 前端架構與使用者體驗 (Frontend UX)

### 5.1 結算畫面的「爆發式回饋 (Burst Feedback)」
由於取消了作答中的即時回饋，交卷後的儀式感必須做到極致。
* 接收到 `EXAM_SETTLED` 事件後，全螢幕播放**圖譜成長動畫**。
* 視覺展現：「結算中... $\rightarrow$ 3 個考點升級為永久掌握 $\rightarrow$ 偵測到 1 個頑固盲點 $\rightarrow$ 總體實力從 65% 上漲至 72%！」

### 5.2 記憶衰退的視覺溫和緩衝
* 若節點因時間流逝觸發衰退（$t_{now} > \text{next\_review\_at}$），顏色應由綠燈平滑過渡為「黃燈閃爍」。
* 點擊該節點時，Tooltip 提示：*「🕒 記憶已衰退，系統建議重新喚醒」*。

### 5.3 滿血復活：記憶喚醒測驗 (Refresh Quiz)
* 為了消解學生對掉分的焦慮，系統提供「一鍵喚醒」功能。
* 點擊後，系統自動打包所有衰退的節點，生成一份極短的「喚醒特訓卷」（如每考點抽 1 題）。
* 若測驗全對，該節點的 $\text{next\_review\_at}$ 大幅向後推延，前端 Effective Progress 瞬間「滿血復活」回 100%。

## 六、 系統防禦與風險管控 (Risks & Mitigations)

### 6.1 交卷海嘯 (Thundering Herd Problem)
* **風險：** 模擬考結束時間（如 11:30）瞬間湧入數千份 100 題的考卷，導致 DB Connection Pool 耗盡。
* **管控：** `POST /api/exams/{exam_id}/submit` 必須設計為 **Fire-and-Forget**。API 只負責將 JSON 寫入 Redis List 並立刻回傳 `202 Accepted`。真正的寫入由 Consumer Worker 平滑消化。前端切換至「成績結算中」的過場動畫等待 WS 推播。

### 6.2 異常中斷與髒狀態 (Interruption & Drafts)
* **風險：** 學生作答 80 題時斷線，若只在交卷時更新，前 80 題紀錄會全部遺失。
* **管控：** 前端實作 LocalStorage，並每隔 30 秒觸發 `PATCH /api/exams/{id}/draft`。此 API 僅覆寫 Redis 中的草稿字串，絕對不觸發狀態機結算。重連時提示學生恢復作答。

### 6.3 考綱拓撲變更的非同步稀釋
* **風險：** 新增考點時，父節點的總權重增加。
* **管控：** 由於進度計算已移至前端，當官方新增考點（`syllabus_topics` 寫入）時，前端下次重整拉取最新圖譜結構時，會自動因為分母變大而算出較低的進度。此時前端比對 Local 快取，若發現總進度下降是因為結構改變，則彈出 Toast：*「🎉 知識庫已擴充！當前總掌握度動態校準為 {new_percent}%」*，將退步感轉化為擴充感。
