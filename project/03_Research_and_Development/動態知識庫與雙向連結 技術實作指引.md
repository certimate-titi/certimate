## 一、 系統架構總覽 (Architecture Overview)

### 1.1 核心定義：有機生長的「數位雙生」
TiTi 的動態知識圖譜揚棄了傳統題庫的「扁平資料夾」與死板的「考綱版本控制」。本系統採用**「混合式架構 (Hybrid Architecture)」**：
* **靜態骨架 (Static Backbone)：** 由 AI 逆向工程萃取的官方考綱（章 $\rightarrow$ 節 $\rightarrow$ 考點）。
* **動態血液 (Dynamic Flow)：** 學生作答的即時表現狀態。
* **有機拓撲 (Organic Topology)：** 當學生上傳新講義，或官方考綱變更（新增/合併）時，系統能即時進行「進度稀釋」與「進度繼承」，確保學習軌跡永不斷鏈。

### 1.2 解決的四大業務痛點
1. **冷啟動問題：** 學生註冊即擁有一棵完整的灰色考綱樹，零孤立節點。
2. **學習缺乏連鎖回饋：** 底層考點的進展，透過「向上渲染 (Upward Propagation)」自動推升父節點（章/節）的進度條。
3. **知識斷層無法定位：** 透過「動態溯源連線」，在學生連續答錯高階題時，精準指出須退回的先備節點。
4. **考綱改版導致資料遺失：** 透過「軟刪除與動態重算」，無痛吸收考點的增刪改。

## 二、 關聯式資料庫設計 (Database Schema)

資料庫需完美支援樹狀結構查詢與節點的生命週期管理。

### 2.1 考綱骨架表：`syllabus_topics`
定義知識節點的層級、權重與軟刪除邏輯。所有學生共用此結構。

```sql
CREATE TABLE syllabus_topics (
    id UUID PRIMARY KEY,
    parent_id UUID REFERENCES syllabus_topics(id), -- 建立樹狀階層
    name VARCHAR(255) NOT NULL,
    depth INT NOT NULL,                            -- 層級 (1: 章, 2: 節, 3: 考點)
    weight FLOAT DEFAULT 1.0,                      -- 在父層級中的佔比權重
    prerequisite_topic_id UUID REFERENCES syllabus_topics(id), -- 先備知識錨點 (溯源用)
    
    -- 有機生長控制欄位
    is_active BOOLEAN DEFAULT TRUE,                -- 是否為現行有效考點 (軟刪除標記)
    merged_into_id UUID REFERENCES syllabus_topics(id), -- 若被官方整併，指向繼承其進度的新節點
    
    created_at TIMESTAMPTZ DEFAULT NOW(),
    updated_at TIMESTAMPTZ DEFAULT NOW()
);

-- 加速樹狀遞迴查詢與活躍節點過濾
CREATE INDEX idx_topics_parent_active ON syllabus_topics(parent_id, is_active);
```

### 2.2 個人狀態聚合表：`user_topic_states`
圖譜前端渲染的唯一資料源，記錄個別學生的進度與狀態。

```sql
CREATE TABLE user_topic_states (
    user_id UUID REFERENCES users(id),
    topic_id UUID REFERENCES syllabus_topics(id),
    
    status VARCHAR(20) DEFAULT 'UNSEEN',           -- UNSEEN, CRITICAL, PENDING, MASTERED
    progress_percentage FLOAT DEFAULT 0.0,         -- 節點掌握度 (0.0 ~ 1.0，由背景動態重算)
    last_updated_at TIMESTAMPTZ DEFAULT NOW(),
    
    PRIMARY KEY (user_id, topic_id)
);
```

### 2.3 雙向連結表：`question_chunk_links`
確保每一道考題都牢牢綁定在教材來源上。

```sql
CREATE TABLE question_chunk_links (
    question_id UUID REFERENCES exam_questions(id),
    chunk_id UUID REFERENCES material_chunks(id),
    topic_id UUID REFERENCES syllabus_topics(id),  -- 冗餘設計：加速圖譜過濾
    relevance_score FLOAT,
    PRIMARY KEY (question_id, chunk_id)
);
```

## 三、 後端演算法與非同步架構 (Backend & Async Processing)

這是系統中最脆弱的效能瓶頸。當考綱變更，**嚴禁使用迴圈單筆更新 (N+1 Update)**，必須採用「記憶體內運算 + 批次更新」的高併發架構。

### 3.1 非同步扇出模型 (Fan-out Task Architecture)
使用 Celery + RabbitMQ/Redis 處理考綱變動事件。

1. **Master Task (事件接收)：** 當新增節點時，撈出有訂閱該考科的 `user_id` 名單（例如 10,000 人）。
2. **Chunking (切塊派發)：** 將名單以每 500 人為一個 Batch，派發 20 個 Sub-Task 給背景 Worker 平行處理。

### 3.2 記憶體內重算與批次更新 (Bulk Update Algorithm)
**Sub-Task 實作規範 (Python/SQLAlchemy 虛擬碼)：**

```python
@celery.task
def batch_recalculate_progress(user_ids_chunk: list[str], root_topic_id: str):
    """
    處理 500 名使用者的進度重算，解決 N+1 查詢與 DB I/O 撐爆問題。
    """
    # 1. 批次讀取 (In-Memory Load)：用 IN 語法一次將 500 人的整棵樹狀態拉進記憶體
    all_states = db.execute(f"""
        SELECT user_id, topic_id, progress_percentage 
        FROM user_topic_states 
        WHERE user_id IN ({','.join(user_ids_chunk)})
    """).fetchall()
    
    # 將資料轉換為 Hash Map: memory_states[user_id][topic_id] = progress
    memory_states = build_hash_map(all_states)
    
    updates_payload = []
    diluted_notifications = []
    
    # 2. 記憶體內遞迴運算 (Zero DB I/O)
    for user_id in user_ids_chunk:
        # 演算法：遞迴加總活躍子節點(is_active=True)的 (進度 * 權重) / 總權重
        new_progress_map = calculate_tree_progress_in_memory(user_id, root_topic_id, memory_states)
        
        for topic_id, new_progress in new_progress_map.items():
            old_progress = memory_states[user_id].get(topic_id, 0)
            if new_progress != old_progress:
                updates_payload.append({
                    "user_id": user_id, 
                    "topic_id": topic_id, 
                    "progress_percentage": new_progress
                })
                # 記錄被稀釋的節點以推播通知
                if new_progress < old_progress:
                    diluted_notifications.append({"user_id": user_id, "topic_id": topic_id, "new_progress": new_progress})

    # 3. 資料庫批次更新 (Bulk Update)
    if updates_payload:
        # 使用 SQLAlchemy 的 bulk_update_mappings 或 PostgreSQL 的 UPDATE ... FROM VALUES
        # 僅消耗 1 次 DB 連線與 1 次 Write I/O
        db.session.bulk_update_mappings(UserTopicState, updates_payload)
        db.session.commit()
        
    # 4. 批次觸發 WebSocket 推播
    batch_send_websocket_events(diluted_notifications)
```

### 3.3 節點軟合併邏輯 (Soft Merge)
1. 將舊節點 `is_active = False`，`merged_into_id = new_uuid`。
2. 背景 Worker 執行 SQL：`UPDATE question_chunk_links SET topic_id = new_uuid WHERE topic_id = old_uuid`。
3. 觸發上述的 `batch_recalculate_progress` 重算新節點的進度。

## 四、 前端架構與使用者體驗 (Frontend UX)

### 4.1 全域狀態與樂觀更新 (Optimistic UI)
為了確保學生作答後的「破關爽感」，不能等待 API 回傳才播動畫。
* 導入 **Zustand** (或 Redux Toolkit)。
* 當呼叫 `POST /api/submit` 時，前端立即在 Client-side 執行向上重算的數學邏輯，直接驅動 UI 進度條上漲與節點變色。若 API 發生 `500 Error`，再無聲 Rollback 狀態。

### 4.2 WebSocket 溫和緩衝通知 (Graceful Degradation)
當系統在背景擴充了新考點（分母變大），導致前端收到 `PROGRESS_DILUTED` 事件時，嚴禁讓進度條默默倒退。
* **觸發機制：** 監聽到事件後，對應節點的進度條應以「黃色閃爍」方式平滑下降。
* **UX 文案：** 畫面右下角彈出 Toast：「🎉 *知識庫已擴充！系統為您納入了新考點，當前總掌握度動態校準為 {new_progress}%，繼續挑戰新領域吧！*」

### 4.3 圖譜視覺化渲染引擎 (React Flow / D3)
* **佈局重構 (Layout Transition)：** 使用 `reactflow` 的自訂 Node。當切換到「考前衝刺視圖」時，過濾掉 `status === 'MASTERED'` 的節點。**必須加上 CSS Transition**，讓節點位置是平滑滑動，而非瞬間閃爍重新排版。
* **動態溯源連線 (Dynamic Tracing Edge)：** * 當 API 回傳某題觸發 `CRITICAL` 狀態，且附帶 `prerequisite_topic_id` 時。
  * 前端動態新增一條 Edge：`<AnimatedEdge source={current_id} target={prereq_id} style={{ stroke: 'red', strokeDasharray: 5 }} />`，引導視線回到基礎節點。

## 五、 進階功能實作：雙向連結跳轉 (Bi-directional Link Navigation)

這解決了「看錯題不知原始出處」的問題。

1. **從考題找講義 (溯源)：**
   * UI 介面：在錯題解析下方加入按鈕【📖 查看教材出處】。
   * 邏輯：API 提供該題綁定的 `chunk_id`，前端 Router 推播跳轉至講義頁，並將該 ID 傳入，觸發講義頁面對該段落文字進行**黃色螢光筆高亮 (Highlight)** 並自動捲動至可視範圍 (Scroll to view)。
2. **從講義找考題 (驗證)：**
   * UI 介面：在 Markdown 渲染器中開發自訂 Plugin。當該段落有對應考題時，於段落右側渲染 Badge `<span class="titi-badge">關聯考題: 5</span>`。
   * 邏輯：點擊 Badge 後，拉出側邊 Drawer (抽屜元件)，呼叫 `GET /api/questions?chunk_id={id}`，讓學生當場進行概念驗證測試。

## 六、 系統監控與預警機制 (Monitoring & Observability)

1. **Celery 任務堆積監控：** 若 RabbitMQ / Redis 中的 `recalculate_progress` Queue 長度超過 1,000，觸發 Slack/Discord 警報，預防背景運算塞車導致前端進度不同步。
2. **孤島節點掃描：** 建立每週執行的 Cron Job，掃描 `question_chunk_links` 與 `syllabus_topics`。若發現 `relevance_score` 低於閾值或無對應 Topic 的題目，列入後台「人工審核池 (Review Pool)」，供編輯手動修正。
3. **DB Deadlock 監控：** 在 PostgreSQL 配置 `log_lock_waits = on`，若發現 `user_topic_states` 有死結發生，立刻檢查 Batch Update 的索引機制是否失效。
