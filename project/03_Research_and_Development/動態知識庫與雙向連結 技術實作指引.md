# 🛠️ TiTi 核心架構：動態知識庫與雙向連結 技術實作指引 (TDD)

**文件版本：** v1.0
**目標受眾：** Backend Engineers, Frontend Engineers, Data Engineers
**專案代號：** TiTi-Graph-Engine

## 一、 產品願景與痛點解決 (Why & Pain Points)

### 1. 為什麼要做這個？(Business Value)
傳統測驗系統的護城河在於「題庫數量」，但這極易被競爭對手複製。TiTi 的護城河在於**「知識網絡的沉澱」**。透過將使用者的作答紀錄轉化為具備狀態的知識圖譜，我們能大幅提高使用者的**轉換成本 (Switching Cost)**。當學生在 TiTi 建立了盤根錯節的個人大腦，他們就無法輕易離開。

### 2. 解決了哪些使用者痛點？
* **痛點 A：錯題本的「認知超載」(Cognitive Overload)**
  * *現況：* 考前累積了 3000 題錯題，列表式呈現讓學生焦慮且無法抓重點。
  * *解法：* 導入**「狀態機分箱」**。系統隱藏「永久掌握」的題目，將視覺焦點強制收斂在「🔥 頑固盲點」，將 3000 題的壓力降至 30 題的核心病灶。
* **痛點 B：「知其然而不知其所以然」(Isolated Knowledge)**
  * *現況：* 看完錯題解析後，依然不懂原始法條或觀念的脈絡。
  * *解法：* 導入**「雙向錨點連結」**。一鍵從錯題跳轉回原始 Markdown 講義段落，實現知識的溯源。

## 二、 核心資料庫設計 (Database Schema)

在現有的 PostgreSQL 架構下，新增以下兩張核心資料表來支撐狀態機與圖譜。

### 1. 狀態機核心：`user_question_states`
這張表取代傳統的 `exam_logs`，用來記錄考題的「生命週期」。

```sql
CREATE TABLE user_question_states (
    user_id UUID REFERENCES users(id),
    question_id UUID REFERENCES exam_questions(id),
    
    -- 狀態機設計
    current_state VARCHAR(20) NOT NULL DEFAULT 'UNSEEN', 
    -- 允許值: UNSEEN(未作答), CRITICAL(盲點), LAPSE(滑鐵盧), PENDING(待鞏固), MASTERED(掌握)
    
    -- 演算法依賴數據
    total_attempts INT DEFAULT 0,
    consecutive_correct_count INT DEFAULT 0,
    ease_factor FLOAT DEFAULT 2.5,  -- SM-2 演算法核心參數
    
    -- 時間戳記
    last_attempt_at TIMESTAMPTZ,
    next_review_at TIMESTAMPTZ,     -- 排程下次出現的時間
    
    PRIMARY KEY (user_id, question_id)
);

-- 建立複合索引以加速「考前衝刺」等 Smart Views 的查詢
CREATE INDEX idx_user_state_review ON user_question_states(user_id, current_state, next_review_at);
```

### 2. 圖譜連結核心：`question_chunk_links`
這張表記錄實體之間的關聯（Edges），在 RAG 出題階段由 AI 寫入。

```sql
CREATE TABLE question_chunk_links (
    question_id UUID REFERENCES exam_questions(id),
    chunk_id UUID REFERENCES material_chunks(id),
    
    -- 擴展性欄位：如果是 AI 標註的關聯，記錄信心度
    relevance_score FLOAT CHECK (relevance_score BETWEEN 0 AND 1),
    link_type VARCHAR(20) DEFAULT 'DIRECT_SOURCE', 
    
    PRIMARY KEY (question_id, chunk_id)
);

CREATE INDEX idx_chunk_to_question ON question_chunk_links(chunk_id);
```

## 三、 後端 API 與演算法實作 (Backend Engineering)

### 1. 狀態機轉移演算法 (State Transition Logic)
當收到使用者的 `submit_answer` 請求時，後端必須執行非同步的狀態轉移。

**業務邏輯 (Python / FastAPI 虛擬碼)：**
```python
def process_answer(user_id: str, question_id: str, is_correct: bool):
    state = db.get_user_question_state(user_id, question_id)
    state.total_attempts += 1
    state.last_attempt_at = now()

    if is_correct:
        state.consecutive_correct_count += 1
        # 狀態升級邏輯
        if state.consecutive_correct_count >= 3:
            state.current_state = 'MASTERED'
            state.next_review_at = None # 封存
        else:
            state.current_state = 'PENDING'
            # SM-2 演算法計算下次複習時間
            interval = calculate_sm2_interval(state.consecutive_correct_count, state.ease_factor)
            state.next_review_at = now() + timedelta(days=interval)
    else:
        # 狀態降級邏輯
        state.consecutive_correct_count = 0
        state.ease_factor = max(1.3, state.ease_factor - 0.2) # 降低簡單度
        
        if state.total_attempts > 1:
            state.current_state = 'CRITICAL'
        elif state.current_state == 'MASTERED':
            state.current_state = 'LAPSE'
            
        state.next_review_at = now() + timedelta(hours=12) # 盲點需盡快複習

    db.commit()
```

### 2. 圖譜資料 API (`GET /api/v1/knowledge-graph`)
前端渲染力導向圖需要 Nodes (節點) 與 Edges (連線)。API 必須將關聯資料扁平化輸出。
* **挑戰：** 為了避免 Payload 過大，必須實作「懶加載 (Lazy Loading)」。初始化只回傳與目標 Chapter 相關的 1-2 層節點，點擊後再 Fetch 更深層的關聯。

## 四、 前端架構與實作 (Frontend Engineering)

### 1. 圖譜視覺化 (Visualizing the Graph)
* **技術選型：** 建議使用 `React Flow` (適合結構化、帶有 UI 元素的節點) 或 `D3.js / Force Graph` (適合處理大量節點的物理碰撞與視覺效果)。
* **渲染邏輯：** 必須依據 `current_state` 動態套用 CSS 樣式。
  * `CRITICAL`: 添加 CSS Pulse 動畫或紅色發光效果 (Glow)。
  * `MASTERED`: 設定 `opacity: 0.3` 降低視覺權重。

### 2. 雙向連結的跳轉機制 (Bi-directional Navigation)
* **實作細節：** 在 Markdown 渲染器 (如 `react-markdown`) 中注入自訂元件。
* **流程：**
  1. API 回傳 Chunk 原文時，夾帶 `related_questions: [...]` 陣列。
  2. 前端在該段落結尾渲染一個 `<RelatedBadge count={...} />`。
  3. 點擊後，觸發全域狀態 (Zustand/Redux)，拉出側邊抽屜 (Drawer) 顯示關聯考題。

## 五、 困難點與技術風險 (Risks & Challenges)

實作動態知識圖譜並非易事，工程團隊必須提前防範以下風險：

### 🔴 風險 1：圖譜渲染的效能瓶頸 (Frontend Performance Crash)
* **情境：** 當學生使用半年後，累積了 500 個教材節點與 3000 個考題節點。如果前端一次渲染 3500 個 DOM 元素並計算物理碰撞，瀏覽器會直接卡死 (FPS 掉到個位數)。
* **工程解法：** * 必須採用 **Canvas 渲染**而非純 DOM (SVG) 渲染。
  * 實作**層級化顯示 (Semantic Zooming)**：縮小時只顯示「章節大節點」，放大到特定比例 (Zoom Level) 時才顯示「考題小節點」。

### 🔴 風險 2：複雜關聯查詢導致資料庫癱瘓 (Database N+1 & JOIN Hell)
* **情境：** 為了畫出「洗錢防制法」底下的所有 Chunk，以及這些 Chunk 關聯的所有 Question，再加上這些 Question 在目前這位使用者的 State，這會是一個跨 4 張表的巨大 JOIN 查詢。若缺乏適當索引，將導致 API 回應時間超過 5 秒。
* **工程解法：**
  * 在 PostgreSQL 善用 `JSON_AGG`，將底層子節點直接在資料庫打包成 JSON 陣列回傳，減少資料傳輸量與後端 Deserialize 的時間。
  * 對於頻繁讀取的「考前衝刺視圖」，必須在 Redis 建立以 `user_id:view_type` 為 Key 的 Cache 層。

### 🔴 風險 3：狀態機的邊界條件 (State Machine Edge Cases)
* **情境：** 如果學生在同一天內反覆重刷同一題，`consecutive_correct_count` 會快速暴增到 3，導致題目錯誤地進入 `MASTERED` (永久掌握) 狀態，這違反了間隔複習的原理。
* **工程解法：** 狀態機必須實作**「冷卻時間 (Cooldown Period)」**。例如：12 小時內的重複作答，雖然紀錄次數，但不計入 `consecutive_correct_count` 的升級條件，強迫記憶必須經過睡眠週期的考驗。

### 🔴 風險 4：冷啟動與孤島節點 (Cold Start Problem)
* **情境：** 剛匯入的官方考古題，AI 若沒有成功將其 Mapping 到任何 `material_chunk`，這題在圖譜上就會變成「孤兒節點 (Orphan Node)」，永遠不會被雙向連結觸發。
* **工程解法：** 建立後台的資料品質監控儀表板 (Data Quality Dashboard)，定期掃描 `question_chunk_links` 表。若發現有題目沒有任何連結，需自動排入背景 Celery Queue，請 AI 再執行一次 Semantic Matching 或是交由人工管理員手動綁定。
