## 一、系統架構概覽

TiTi 是一套 AI 驅動的證照考試備考 SaaS 平台，採用前後端分離架構，以混合 RAG（Retrieval-Augmented Generation）系統為核心引擎，結合公共考古題資料庫與使用者個人素材，實現高品質、個人化的考題生成。

## 二、資料層設計

### 2.1 雙軌儲存機制（Dual-Storage Strategy）

**核心原則：必須保留解析後的 Markdown (.md) 檔案，絕對不能轉換成向量庫後即拋棄。原始檔案（PDF、圖片等）在解析狀態確認為 `COMPLETED` 後才執行刪除；若解析失敗 (`FAILED`)，原始檔必須保留，以支援使用者觸發「重新解析 (Retry)」。**

三層儲存架構如下：

| 層級 | 儲存引擎 | 職責 |
|------|---------|------|
| **Markdown 文本庫** | Google Cloud Storage (GCS) | 解析後的 `.md` 永久保存，為整個系統的「真理之源」 |
| **關聯式資料庫** | PostgreSQL (Cloud SQL) | 文件 Metadata、結構化考題題庫、使用者學習排程、pg tsvector 全文檢索 |
| **向量索引** | pgvector (PostgreSQL 擴充套件) | 切塊字串 (Chunks) 與高維度 Embedding 陣列，做為語意搜尋與關聯運算的索引器 |

向量索引層完全依賴 GCS 的 `.md` 檔為基底。即使向量索引損毀或清空，只要 `.md` 存在，可隨時在背景重新執行 Re-embedding。

### 2.2 雙軌儲存的決策理由

#### (1) 使用者溯源與防幻覺 (Hallucination)

向量資料庫儲存的是將文字「切塊 (Chunking)」後的碎肉狀態。如果使用者認為 AI 產出的考題或解題邏輯有誤，並想檢視原始講義的上下文，系統無法依靠獨立的「500 字元碎塊」還原整份文件的排版與脈絡。只有保留完整的 `.md` 檔，系統才能精確標示：「這題出自第三章第 2 節」，並讓使用者點開查看完整段落。

#### (2) 模型演算法升級與無縫遷移（最致命風險）

AI 領域的 Embedding 模型更新極為頻繁，且費用持續降低。**向量資料的維度與幾何空間在不同模型之間是完全「互不相容」的。** 未來若系統需要升級更好的演算法、改用本地模型開源節流，或是因應新功能改變切塊大小 (Chunk Size)，我們都**必須**具備原始的 `.md` 文字檔才能「重新計算所有向量 (Re-embedding)」。

#### (3) 混合搜尋的必要性 (Hybrid Search)

向量檢索雖擅長「語意相似度」，但對於「精準的關鍵字搜索（例如特定的程式錯誤代碼 `Err_0x55` 或專有術語）」表現極差。保留原始純文字，系統才能結合 **PostgreSQL 的 Full Text Search (pg tsvector)**，執行「pgvector 語意 + 精準關鍵字」的混合搜尋，達成最精準的配題。

#### (4) 資料匯出與便攜性 (Data Portability)

若未來規劃「個人化講義匯出」功能，或需對接 Notion、Obsidian、Google Drive 等外部筆記軟體，系統必須提供排版完整且人類可讀的 Markdown 檔案。Markdown 屬於純文字格式，檔案極度輕量化，其維護與儲存成本幾乎可以忽略不計，因此「保留輕量的原檔以換取極大的系統彈性」是效益最高的決策。

### 2.5 pgvector 索引策略

所有向量索引統一使用 PostgreSQL pgvector 擴充套件，在同一個資料庫實例中管理：

```sql
-- 啟用 pgvector 擴充套件
CREATE EXTENSION IF NOT EXISTS vector;

-- 公共向量表
CREATE TABLE public_exam_vectors (
    vector_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    question_id UUID REFERENCES exam_questions(question_id),
    topic_id UUID REFERENCES syllabus_topics(topic_id),
    embedding vector(1536),  -- text-embedding-3-large
    exam_name TEXT,
    year INT,
    difficulty INT,
    question_type TEXT,
    answer TEXT
);

-- 建立 HNSW 索引加速近似最近鄰搜尋
CREATE INDEX idx_public_vectors_embedding
    ON public_exam_vectors USING hnsw (embedding vector_cosine_ops);

-- 複合索引加速多條件過濾
CREATE INDEX idx_public_vectors_topic ON public_exam_vectors(topic_id);
CREATE INDEX idx_public_vectors_exam ON public_exam_vectors(exam_name);
CREATE INDEX idx_public_vectors_difficulty ON public_exam_vectors(difficulty);

-- 個人向量表（透過 user_id 列級隔離）
CREATE TABLE personal_vectors (
    vector_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID NOT NULL,
    chunk_id UUID REFERENCES material_chunks(chunk_id),
    topic_id UUID,
    embedding vector(1536),
    source_type TEXT,
    quality_score FLOAT,
    confidence FLOAT
);

CREATE INDEX idx_personal_vectors_embedding
    ON personal_vectors USING hnsw (embedding vector_cosine_ops);
CREATE INDEX idx_personal_vectors_user_topic
    ON personal_vectors(user_id, topic_id);
CREATE INDEX idx_personal_vectors_quality
    ON personal_vectors(quality_score);
```

## 三、混合 RAG 系統

TiTi 的 RAG 系統分為兩條平行的資料流，最終在「出題規劃層」匯合，產生一份結構化試卷。

### 3.1 RAG 架構流程

```
┌─────────────────────────────────────────────────────────────────┐
│                        使用者請求（出題）                          │
└────────────────────────────┬────────────────────────────────────┘
                             │
                    ┌────────▼────────┐
                    │   出題規劃層      │  ← 大綱考點樹 + 個人弱點分析
                    │  (Exam Planner)  │     決定「要出哪些考點、幾題、難度」
                    └────────┬────────┘
                             │  考點清單（topic_list）
           ┌─────────────────┼─────────────────┐
           │                                   │
  ┌────────▼────────┐                ┌─────────▼───────┐
  │   公共層 RAG     │                │   個人層 RAG     │
  │  Public Retriever│                │ Personal Retriever│
  │                 │                │                  │
  │ • 考古題向量庫   │                │ • 使用者素材向量庫 │
  │ • 命題大綱       │                │ • 轉譯/解析後文本  │
  │ • 標準答案       │                │ • 個人筆記        │
  └────────┬────────┘                └─────────┬────────┘
           │  召回結果（高信度）               │  召回結果（中/低信度）
           └─────────────────┬───────────────┘
                             │
                    ┌────────▼────────┐
                    │   結果合併層      │  ← 去重、排序、信度標注
                    │  (Result Merger) │
                    └────────┬────────┘
                             │
                    ┌────────▼────────┐
                    │   題目生成層      │  ← LLM 生成 + 答案驗證
                    │ (Question Gen)   │
                    └────────┬────────┘
                             │
                    ┌────────▼────────┐
                    │   試卷組裝層      │  ← 結構校驗 + 信度標示輸出
                    │  (Exam Builder)  │
                    └─────────────────┘
```

**設計核心原則：公共層是品質的地板，個人層是個人化的天花板。混合 RAG 的責任不是「混在一起」，而是讓兩層各司其職，在正確的時機以正確的信度提供正確的素材。**

### 3.2 信度標籤系統（Confidence Labels）

所有生成的考題都會標注信度標籤，讓使用者理解題目來源與可信程度：

| 標籤 | 意義 | 來源條件 |
|------|------|---------|
| 🟢 綠色 | 高信度 | 公共考古題直接使用，有官方標準答案 |
| 🟡 黃色 | 中信度 | 個人素材生成且 quality_score >= 0.8，或個人 + 公共混合召回 |
| 🔴 紅色 | 低信度 | 個人素材生成且 quality_score < 0.8，或答案驗證不一致 |

### 3.3 出題規劃層（Exam Planner）

這是 TiTi 與 NotebookLM 最關鍵的差異——**先規劃再召回，而非先召回再組合**。

#### 3.3.1 考點清單生成流程

```python
def generate_topic_plan(
    user_id: str,
    exam_name: str,
    total_questions: int,
    mode: str  # "standard" | "weakness_focus" | "custom"
) -> TopicPlan:

    # Step 1：從大綱取得考點權重
    topics = get_syllabus_topics(exam_name)

    # Step 2：取得使用者弱點分布
    weakness_map = get_weakness_map(user_id, exam_name)
    # weakness_map = { topic_id: weak_score }  # 0=強 1=弱

    # Step 3：依模式計算各考點出題數
    if mode == "standard":
        # 完全依大綱比例
        allocation = allocate_by_weight(topics, total_questions)

    elif mode == "weakness_focus":
        # 大綱比例 * 弱點加權（弱點考點多出 1.5-2x）
        allocation = allocate_with_weakness(
            topics, total_questions, weakness_map, boost=1.8
        )

    elif mode == "custom":
        # 使用者手動指定考點與題數
        allocation = get_custom_allocation(user_id)

    # Step 4：檢查每個考點的素材覆蓋度
    for topic in allocation:
        coverage = get_coverage_status(user_id, topic.topic_id)
        topic.coverage_status = coverage   # sufficient/partial/missing
        topic.preferred_source = decide_source(coverage)
        # preferred_source:
        #   sufficient → "personal_first"（優先用個人素材）
        #   partial    → "mixed"（個人 + 公共混合）
        #   missing    → "public_only"（純公共考古題）

    return TopicPlan(topics=allocation)
```

### 3.4 混合 RAG 召回設計

#### 3.4.1 召回策略決策樹

```
for each topic in TopicPlan:

    preferred_source = topic.preferred_source

    if preferred_source == "public_only":
        │
        └─→ 僅從公共考古題召回
            results = public_retriever.search(
                topic_id=topic.topic_id,
                n=topic.count * 3,   # 多召回供篩選
                exclude_seen=True    # 排除使用者已做過的題
            )

    elif preferred_source == "personal_first":
        │
        ├─→ 先從個人素材召回
        │   personal_results = personal_retriever.search(
        │       user_id=user_id,
        │       topic_id=topic.topic_id,
        │       n=topic.count * 2
        │   )
        │
        └─→ 不足時補充公共考古題
            if len(personal_results) < topic.count:
                gap = topic.count - len(personal_results)
                public_results = public_retriever.search(
                    topic_id=topic.topic_id, n=gap * 2
                )
            confidence_label = "🟡"

    elif preferred_source == "mixed":
        │
        ├─→ 同時召回兩層，各取一半
        │   personal_results = personal_retriever.search(...)
        │   public_results   = public_retriever.search(...)
        │
        └─→ 合併後排序
            confidence_label = "🟡" or "🔴"（依個人素材 quality_score）
```

#### 3.4.2 向量檢索實作（pgvector）

**公共層檢索：**

```python
def public_retriever_search(
    topic_id: str,
    n: int,
    exam_name: str,
    difficulty_range: tuple = (1, 5),
    exclude_question_ids: list = []
) -> list[PublicChunk]:

    # Hybrid Search：pgvector 語意相似度 + SQL 條件過濾
    query_embedding = embed(topic_id)  # 用考點名稱做 query

    results = db.execute(text("""
        SELECT vector_id, question_id, topic_id, exam_name,
               difficulty, question_type, answer,
               1 - (embedding <=> :query_vector) AS similarity
        FROM public_exam_vectors
        WHERE topic_id = :topic_id
          AND exam_name = :exam_name
          AND difficulty BETWEEN :diff_min AND :diff_max
          AND question_id != ALL(:exclude_ids)
          AND 1 - (embedding <=> :query_vector) >= 0.75
        ORDER BY embedding <=> :query_vector
        LIMIT :top_k
    """), {
        "query_vector": query_embedding,
        "topic_id": topic_id,
        "exam_name": exam_name,
        "diff_min": difficulty_range[0],
        "diff_max": difficulty_range[1],
        "exclude_ids": exclude_question_ids,
        "top_k": n,
    }).fetchall()

    return [PublicChunk(
        question_id=r.question_id,
        text=r.text,
        answer=r.answer,
        difficulty=r.difficulty,
        source="public",
        confidence="🟢"
    ) for r in results]
```

```python
def personal_retriever_search(
    user_id: str,
    topic_id: str,
    n: int,
    min_quality: float = 0.5
) -> list[PersonalChunk]:

    query_embedding = embed(topic_id)

    results = db.execute(text("""
        SELECT vector_id, chunk_id, topic_id, source_type,
               quality_score, confidence,
               1 - (embedding <=> :query_vector) AS similarity
        FROM personal_vectors
        WHERE user_id = :user_id
          AND topic_id = :topic_id
          AND quality_score >= :min_quality
          AND 1 - (embedding <=> :query_vector) >= 0.70
        ORDER BY embedding <=> :query_vector
        LIMIT :top_k
    """), {
        "query_vector": query_embedding,
        "user_id": user_id,
        "topic_id": topic_id,
        "min_quality": min_quality,
        "top_k": n,
    }).fetchall()

    return [PersonalChunk(
        chunk_id=r.chunk_id,
        text=r.text,
        source_type=r.source_type,
        quality_score=r.quality_score,
        source="personal",
        confidence=decide_confidence(r.quality_score)
        # quality >= 0.8 → 🟡  |  quality < 0.8 → 🔴
    ) for r in results]
```

**混合搜尋（pgvector 語意 + pg tsvector 關鍵字）：**

```python
def hybrid_search(
    query_text: str,
    user_id: str,
    topic_id: str,
    n: int,
    semantic_weight: float = 0.7,
    keyword_weight: float = 0.3
) -> list[PersonalChunk]:
    """
    結合 pgvector 語意相似度與 pg tsvector 全文檢索，
    以加權分數排序實現混合搜尋。
    """
    query_embedding = embed(query_text)

    results = db.execute(text("""
        SELECT chunk_id, chunk_text,
               (1 - (pv.embedding <=> :query_vector)) * :sem_w
               + ts_rank(mc.tsv_content, plainto_tsquery('chinese', :query_text)) * :kw_w
               AS hybrid_score
        FROM personal_vectors pv
        JOIN material_chunks mc ON pv.chunk_id = mc.chunk_id
        WHERE pv.user_id = :user_id
          AND pv.topic_id = :topic_id
        ORDER BY hybrid_score DESC
        LIMIT :top_k
    """), {
        "query_vector": query_embedding,
        "query_text": query_text,
        "user_id": user_id,
        "topic_id": topic_id,
        "sem_w": semantic_weight,
        "kw_w": keyword_weight,
        "top_k": n,
    }).fetchall()

    return results
```

#### 3.4.3 結果合併層（Result Merger）

```python
def merge_results(
    public_chunks: list[PublicChunk],
    personal_chunks: list[PersonalChunk],
    topic: TopicAllocation
) -> list[MergedChunk]:

    all_chunks = public_chunks + personal_chunks

    # Step 1：去重（相似度 > 0.92 視為重複，保留公共層版本）
    deduped = deduplicate(all_chunks, threshold=0.92, prefer="public")

    # Step 2：排序（公共 > 個人高品質 > 個人低品質）
    source_priority = {"public": 3, "personal_high": 2, "personal_low": 1}
    sorted_chunks = sorted(
        deduped,
        key=lambda c: (source_priority[c.source_tier], c.similarity_score),
        reverse=True
    )

    # Step 3：取前 N 筆
    return sorted_chunks[:topic.count * 2]   # 保留 2x 供 LLM 篩選
```

#### 3.5.2 Chunking 策略

考試素材的 chunking 有別於一般文件，需要考慮考點邊界：

```python
def exam_aware_chunking(text: str, topic_boundaries: list) -> list[Chunk]:
    """
    規則：
    1. 優先以「考點邊界」為切割點（章節標題、條號）
    2. 每塊維持 300-600 tokens
    3. 相鄰塊保留 50 tokens overlap，確保上下文連貫
    4. 不在題目中間切割（若素材含有練習題）
    """
    chunks = []
    current_chunk = ""
    current_topic = None

    for sentence in sentences(text):
        detected_topic = detect_topic_boundary(sentence, topic_boundaries)

        # 遇到新考點邊界 → 強制切割
        if detected_topic and detected_topic != current_topic:
            if current_chunk:
                chunks.append(Chunk(text=current_chunk, topic_id=current_topic))
            current_chunk = sentence
            current_topic = detected_topic

        # 超過大小上限 → 在語意斷點切割
        elif token_count(current_chunk + sentence) > 600:
            chunks.append(Chunk(text=current_chunk, topic_id=current_topic))
            current_chunk = get_overlap(current_chunk, 50) + sentence

        else:
            current_chunk += sentence

    return chunks
```

**Chunking 參數摘要：**

| 參數 | 數值 | 說明 |
|------|------|------|
| Chunk 大小 | 300-600 tokens | 兼顧語意完整性與檢索精度 |
| Overlap | 50 tokens | 確保相鄰塊間上下文連貫 |
| 切割優先順序 | 考點邊界 > 語意斷點 > 大小上限 | 不在題目中間切割 |
| 去重閾值 | 相似度 > 0.92 | 視為重複，保留公共層版本 |

```python
    )
```

```python
def validate_answer(
    question: GeneratedQuestion,
    source_chunk: MergedChunk,
    exam_context: ExamContext
) -> GeneratedQuestion:

    # 方法一：讓另一個 LLM 獨立作答，檢查是否選同一答案
    verification_answer = llm_judge.answer(
        question=question.text,
        options=question.options,
        context=source_chunk.text
    )

    if verification_answer != question.answer:
        # 答案不一致 → 降低信度標示 or 放棄此題
        question.confidence = "🔴"
        question.needs_review = True

    # 方法二：選擇題干擾項檢查
    # 確保錯誤選項不會「太明顯」或「也說得通」
    distractor_score = evaluate_distractors(question)
    if distractor_score < 0.6:
        question.needs_review = True

    return question
```

## 六、擴充性設計

TiTi 採用 GCP Serverless 無伺服器架構，賦予專案極高的未來擴充與轉型便利性。當平台度過早期的 PoC 階段並開始獲利後，可以輕易且低門檻地往以下四個維度進行擴充。

### 6.1 流量層級的無縫擴容（Traffic Scalability）

- **Cloud Run 的 Auto-Scaling**：目前的運算核心（前後端 API）都架構在 Cloud Run 上。這意味著當考季來臨、流量瞬間從 100 人暴增到 10,000 人時，系統會**自動在幾秒內長出新的實例 (Instances) 來承載流量**，流量退去後又自動縮容至 0。完全不需要人工介入開機或關機。
- **資料庫升級平滑**：初期考量成本使用的微型 Cloud SQL（含 pgvector 擴充套件），未來只要在 GCP 控制台點擊幾下，就能不中斷服務地升級為具備高可用性 (HA) 與多讀取複本 (Read Replicas) 的企業級叢集。pgvector 索引隨資料庫自動遷移，無需額外處理。

### 6.2 功能生態系的橫向擴充（MCP Ecosystem）

透過 **MCP (Model Context Protocol) 架構**，未來要新增任何「輸入源」都非常簡單，不需要更動 TiTi 的核心程式碼。這就像是在替系統外掛裝備：

1. **GitHub Repository 解析器**：寫一個 MCP Server，讓使用者輸入一個 GitHub 網址，系統就能直接幫他針對某個開源專案的程式碼出考題。
2. **Podcast / 音檔解析器**：串接 Whisper 的 MCP Server，讓通勤族丟入一段 Podcast 音檔連結，回家就能做測驗。
3. **Notion / Google Drive 匯入器**：透過 MCP 授權，直接一鍵將使用者的線上筆記本變成考題。

### 6.3 B2B 企業市場的平行擴張（Multi-Tenancy）

- **多租戶架構準備**：由於架構切分乾淨，未來若有補習班或企業想採購這套系統，我們只需在資料庫加上 `tenant_id`（租戶 ID），就能輕易為每個企業開出「獨立專屬的測驗後台」。pgvector 向量索引同樣可透過 `tenant_id` 實現租戶級資料隔離。
- **API 經濟（API-as-a-Service）**：TiTi 的「異質講義轉考題引擎」本身就是一個極具價值的資產。未來可以不只做 B2C 的網頁版，而是將引擎包裝成 API 販售給其他教育平台 (EdTech)，讓他們按次呼叫付費 (SaaS API Model)。

### 6.4 LLM 模型的無痛抽換（Model Flexibility）

- **不被單一廠商綁架**：由於核心是標準的 RAG（檢索增強生成），且我們已經抽象化了 AI 呼叫層。如果明天 OpenAI 漲價，或是 Llama-4 表現超越了 Gemini，我們只需在設定檔中抽換 API Key 與 Endpoint，系統就能在一夜之間切換大腦。
- **地端化 / 私有化部署**：當我們收集了足夠多的「學生錯題對話記錄」後，未來完全有機會自行 Fine-tune 一個開源的 Llama 模型，並部署在我們自己的 GPU 伺服器上，徹底擺脫對雲端大廠 API 的依賴，使得單次考題生成成本真正趨近於 0。
- **Embedding 模型升級無痛**：由於 GCS 上永久保留完整的 `.md` 原檔（見第二章雙軌儲存機制），當 Embedding 模型升級時，只需在背景重新執行 Re-embedding 寫入 pgvector，無需重新收集使用者素材。
