# 資料儲存與向量化架構決策

## 決策背景
本系統支援將 PDF、Word、錄音檔或 YouTube 影片解析為知識點並轉化為考題與心智圖。在資料儲存設計上，我們面臨是否要在生成「向量資料庫 (Vector Database)」後，為節省空間而丟棄原始解析文本的抉擇。

## 架構決策：雙軌儲存機制 (Dual-Storage Strategy)
**核心原則：強烈建議必須保留原始解析的 Markdown (.md) 檔案，絕對不能轉換成向量庫後即拋棄。**

建議的架構處理流程如下：

1. **原始檔案處理庫 (Blob Storage / 檔案系統)**
   將使用者上傳的內容轉化後，標準的 **Markdown (.md)** 文件應存放在雲端硬碟 (如 AWS S3 或 GCS) 或伺服器本地端中妥善保存。
2. **關聯式資料庫 (Relational DB, 如 SQLite / PostgreSQL)**
   負責記錄文件的 Metadata（標題、擁有者、上傳時間、檔案路徑）與結構化產出的「考題題庫（Flashcards/Items）」。
3. **向量資料庫 (Vector Index, 如 VSS)**
   專門用來存放「碎塊的字串 (Chunks)」與「高維度數值陣列 (Embeddings)」。此層僅做為「語意搜尋引擎與關聯運算的索引器」，其存活完全依賴原始 `.md` 檔。即使向量庫因為異常損毀或清空，只要 `.md` 檔還在，隨時都能在背景重新生成向量。

---

## 決策原因與風險分析

### 1. 使用者溯源與防幻覺 (Hallucination)
向量資料庫儲存的是將文字「切塊 (Chunking)」後的碎肉狀態。如果使用者認為 AI 產出的考題或解題邏輯有誤，並想檢視原始講義的上下文，系統無法依靠獨立的「500 字元碎塊」還原整份文件的排版與脈絡。
只有保留完整的 `.md` 檔，系統才能精確標示：「這題出自第三章第 2 節」，並讓使用者點開查看完整段落，達到防護幻覺並確保知識正確性的目的。

### 2. 模型演算法升級與無縫遷移（最致命風險）
AI 領域的 Embedding 模型更新極為頻繁，且費用持續降低。**向量資料的維度與幾何空間在不同模型之間是完全「互不相容」的。**
未來若系統需要升級更好的演算法、改用本地模型開源節流，或是因應新功能改變切塊大小 (Chunk Size)，我們都**必須**具備原始的 `.md` 文字檔才能「重新計算所有向量 (Re-embedding)」。如果直接捨棄原檔，整個系統與使用者過去累積的數據將永遠被鎖死在舊版模型中，失去升級彈性。

### 3. 混合搜尋的必要性 (Hybrid Search)
知識點的串聯依賴「關聯性檢索 (The Linker)」。向量檢索雖擅長「語意相似度」，但對於「精準的關鍵字搜索（例如特定的程式錯誤代碼 `Err_0x55` 或專有術語）」表現極差。保留原始純文字，系統才能夠結合關聯式資料庫的全文搜尋引擎 (如 SQLite 的 FTS5)，執行「向量語意 + 精準關鍵字」的混合搜尋，達成最精準的配題。

### 4. 資料匯出與便攜性 (Data Portability)
若未來規劃「個人化講義匯出」功能，或需對接如 Notion, Obsidian, Google Drive 等外部筆記軟體，系統必須提供排版完整且人類可讀的 Markdown 檔案，而非機器才懂的向量陣列。此外，Markdown 屬於純文字格式，檔案極度輕量化，其維護與儲存成本幾乎可以忽略不計，因此「保留輕量的原檔以換取極大的系統彈性」是效益最高的決策。
